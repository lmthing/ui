# Forms, text fields, and choice controls

## Form and field anatomy

Include a persistent label, appropriate input, optional format/example, and a nearby error with a way forward. A placeholder is a hint and disappears; it can't be the only name or format instruction. Size fields to the answer without limiting the content to the visible width. Use the keyboard and return action that match the data (`Next`, `Search`, `Done`), allow paste/autofill, and use secure fields for private data. A multiline view or composer is better than a narrow single-line field for messages. Let people clear a long single-line field when useful, with an accessible name on the clear action. Don't substitute segmented one-character inputs for the system's code-entry/autofill experience without equivalent paste and accessibility.

At 390 wide, stack ordinary form rows, use a 44 × 44 pt touch footprint on native, and let the row grow when a label or error wraps. Use two columns only for tightly related short values that survive type growth. Start with about 16 logical units between independent fields (a proposal, not an Apple number). Keep the submit action and currently edited field revealable with the keyboard open; zero error state is not the same as empty or pristine. Validate at a useful moment: cheap help while typing if it won't reject normal incomplete input; on leaving the field or on submission for rules that need a finished value. During submission keep the draft and distinguish saving, saved, retryable failure and field validation errors.

## Which control fits the data?

| Family            | Anatomy, semantics and variants                                                                                                                                         | Do and don't                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Picker            | A label and current value, with an ordered choice list. Native date styles include compact, inline, and wheels; modes include date, time, date and time, and countdown. | Compact is useful to save rows; inline is useful when the calendar is the task; wheels can handle predictable ordered values. Use day, locale and time zone deliberately. Pick minute granularity that matches the task, not false precision. Don't go to another screen for a simple choice unless the options need an actual browsing task. |
| Toggle            | Name of a binary property, track/thumb or on/off button, and visible and programmatic state.                                                                            | iOS favors switches in list rows and toggle buttons elsewhere. Use a switch for a setting, not an action like Send. Make position/shape convey state as well as color. Use checkboxes for independent selection and explicit single-choice semantics for mutually exclusive rows.                                                             |
| Slider            | Named range, current value, track and thumb, with useful endpoint or unit labels.                                                                                       | Minimum at leading (or bottom), maximum at trailing (or top). Update the displayed value during drag. Add an exact field or stepper for meaningful precision; don't require dragging. Respect system audio volume controls on iOS.                                                                                                            |
| Stepper           | Decrement and increment actions near a visible value with unit and bounds.                                                                                              | Expose independent targets and indicate the end conditions; pair with direct entry for large jumps. Don't repurpose the visually read-only counter as the only action target.                                                                                                                                                                 |
| Segmented control | Small set of related choices, with a shared container and an obvious selection.                                                                                         | Apple says around five segments at most on iPhone; three or four concise labels are a safer 390-wide starting point. Keep widths and mode consistent; don't mix symbol-only and text-only options. Use a list/picker when labels or count no longer fit. Don't replace top-level tab navigation with a segmented control.                     |
| Rating or scale   | Range or set of levels with a clear question, current value and unselected state; read-only ratings differ from interactive ratings.                                    | Give each value a meaningful name and room to act. A five-value layout with 44-unit targets needs at least 220 units before gaps. A visually filled half-star in a read-only scale isn't implicitly a selectable half-step.                                                                                                                   |

On native, prefer system inputs for editing, autofill, keyboard behaviors and accessibility adjustments. On web choose semantic controls (`input`, `select`, `textarea`, radio/checkbox, and range where appropriate), use `inputmode` and `autocomplete` deliberately, link errors and hints, and test standard editing and keyboard commands. A CSS-styled “switch” or “slider” still needs state, bounds, a useful name, and equivalent input behavior.

## For lmthing

`Field` and `Composer` own short and long entry; `Choice` is preferable to custom input for a known choice; use `Checklist`, `Segmented`, and `Scale` for their different meanings. Use `KitInput`, `KitChip`, `KitCheck`, `KitSlider`, and the existing list toggle treatment instead of drawing new inputs per pack. Audit calendar date selection versus scheduling and exact quantities in booking, kitchen, commerce and health. Gaps to verify: shared date/time picker behavior, an addressed accessible stepper paired with exact entry, and error recovery/focus with a pinned keyboard action. Keep permission or service operations host-owned, even if reached through a form.
