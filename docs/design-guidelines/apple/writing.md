# Writing and tone

Voice is the vocabulary and personality the product keeps. Tone responds to the moment: calm and precise during a payment error, warm on a significant success, spare while someone's hands are busy. Write the most important fact first, use plain language and active voice, and read the copy aloud. Avoid unclear “we,” unnecessary possessives, blame, jargon, and humor in costly or stressful situations. Use a terminology list for the same object and action across screens, pack text, VoiceOver names and spoken replies. Choose a consistent capitalization pattern per element; follow native conventions (for example, title case for menu items) when using system-like UI.

| Surface                     | What the words need to do                                                                                         | Example                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Navigation or section       | Identify where you are or what is beneath the title. Don't repeat the app name.                                   | `Delivery history`                                                           |
| Action                      | Start with the action, adding the object if it removes ambiguity. Use Next or Continue consistently in one flow.  | `Save draft`, `Share a copy`                                                 |
| Field                       | Name the data persistently and give an example only if it clarifies format.                                       | `Pickup time`; hint `For example, 9:30 AM`                                   |
| Field error                 | Name the rule or show a way to fix the problem; keep the input and put feedback nearby.                           | `Choose a pickup time after 8 AM.`                                           |
| Empty, filtered, or offline | Say what is absent or stale and what can happen next.                                                             | `No runs match these filters.` / `Clear filters`; `Last updated at 9:30 AM.` |
| Permission                  | Explain the specific resource and benefit; let the OS name its buttons.                                           | `Use your location to show pickup spots near you.`                           |
| Confirmation                | State the consequence, name each outcome, and give an obvious safe action.                                        | `Delete this draft?` / `Keep draft` / `Delete draft`                         |
| Pending or success          | Match the language to the evidence; distinguish a queued request from a result.                                   | `Waiting to send` versus `Request sent to Alex`                              |
| Assistive name              | Name the function or relevant image content. Don't duplicate a nearby label or announce “button” inside the name. | `Clear search` rather than `X icon`                                          |

Use text that fits the delivery mechanism: ephemeral or interruptive channels should carry only what needs that attention. A banner can describe what happened without forcing a decision; an alert should ask for one. A notification needs only useful, privacy-safe context, not an app name the platform already displayed. A permission explanation is a brief complete sentence, not a fake prompt. When an action opens a choice or details, make the label honest about the next step rather than promising a completed action.

At 390 wide, first try buttons with one short phrase and a one- or two-line explanation, as a review target, not a truncation rule. At large text and in translation let content wrap and layouts grow. Use logical terms that work in speech, keyboard help, and screen readers. On web, write links to make sense out of context, explicitly label inputs, and distinguish a destination link from a command button. On native use localized system labels when applicable; respect OS speech and Voice Control names.

## For lmthing

Keep model instructions in the component prompt and user-facing language in prop content, the cast, pack language files or shared words, as the component guide requires. Preserve the same entity names in `Button`, `Field`, `Empty`, `Banner`, `Success`, `Sheet` and `HandoffReceipt`, including spoken and typed flows. A model can describe what a request is for, but trusted receipt wording must follow host state and tier. Review privacy-sensitive content in health, parenting, commerce, and team packs. Gap: add paired copy examples for empty versus filtered, draft versus queued versus done, and destructive versus undoable to journey templates; check them at 390 and with enlarged type.
