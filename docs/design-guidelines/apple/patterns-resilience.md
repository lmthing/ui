# Resilient patterns: states, undo, offline, and handoffs

## State isn't one generic notice

| Condition                        | Show                                                                                                                                       | Next move or transition                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| First-use empty                  | Name what belongs here and make the first useful action apparent.                                                                          | One invitation, not an error or a generic congratulations graphic.                                                                                                                               |
| No matches or nothing left to do | Acknowledge the query/filter or the completed work.                                                                                        | Clear filters, change search, or return to another task. Don't treat all empty states as an invitation to create.                                                                                |
| Loading without data             | Show useful structure quickly, with a placeholder matching the filled layout; use a progress indicator if the person is waiting on a task. | Preserve action/content positions and hide placeholders from assistive reading. Let people continue or cancel when feasible. Publish real progress when measured, not an arbitrary climb to 99%. |
| Refreshing with data             | Keep usable prior content; attach quiet loading feedback or timestamp.                                                                     | Replace or merge in place; don't blink back to a blank skeleton.                                                                                                                                 |
| Connection lost / stale data     | Say what is still available and how current it is; keep local actions usable.                                                              | Preserve the draft, distinguish queued from sent, offer retry or cancel, and gate only actions that need a fresh result.                                                                         |
| Failed or partially complete     | Name the affected field/item and the outcome with a real remedy.                                                                           | Preserve valid work; allow a focused retry without repeating accepted pieces. If the remote outcome is unknown, check status before resubmitting.                                                |
| Significant success              | Confirm what happened with the item or a concise receipt.                                                                                  | Let the recipient continue. Announce success once; ordinary routine edits may only need inline change.                                                                                           |

Use inline feedback first, then a nonblocking banner or durable receipt for effects that matter elsewhere, and an alert only for critical interruption. At 390 wide, reserve room in the same content column for status and recovery without pushing a fixed footer over the focused row. If a card grows or collapses, keep the person anchored to what they're working on. Don't use color, motion, or haptics as the only proof of a status.

## Undo and offline

- **Undo an action** rather than warning about every reversible edit. Name the effect (`Undo move`), preserve object identity, visibly restore position/selection, and support repeated undo and redo where the data model permits. Provide an explicit equivalent for native undo gestures and keyboard shortcuts. A short-lived banner can't be the only route for a time-sensitive or high-impact undo.
- **Offline isn't empty.** Use cached data when it's still safe to read and mark its age. If queueing is supported, distinguish local draft, queued, syncing, acknowledged and rejected; provide visible recovery for conflicts and cancellation where possible. Don't say a person was notified or a payment completed before acknowledgement. If queueing is unsupported or unsafe, keep the draft and state what can't complete offline.
- **Native versus web:** native `URLSession` can wait for connectivity when establishing a connection; a connection dropped later still needs recovery. Request results are stronger evidence than a connectivity indicator; on web, test requests even if a network signal says online. Exercise cold start offline, disconnect during a save, resuming stale data, and reconnecting after retry. These UI state transitions are synthesis proposals based on Apple's guidance on launching, loading, feedback, and connectivity, not a standalone Apple offline spec.

## Accounts, ratings, sharing

- **Accounts:** demonstrate value before requiring sign-in. State why it is needed and use the available method's real name (Sign in with Apple or a passkey where appropriate). If the app supports account creation, provide in-app deletion initiation, clear consequences and expected timing; explain subscription handling separately. For lmthing's accountless launch, don't insert this into the shell journey. It may apply to a generated account-bearing product.
- **Ratings:** defer to meaningful engagement and a natural pause, never after every success or on first launch. Apple's StoreKit controls display and caps it at three occurrences in 365 days for someone who hasn't already rated or reviewed on that device; its API might not show anything. A catalog `Scale` recording a rating within a workflow is not an App Store review prompt.
- **Sharing:** surface a standard Share action near the object. Use the native share sheet or supported web share with a clear fallback, such as copying a link after an explicit action. Distinguish sending a copy from collaborating on the same item; state who can access it and whether they can view or edit. Keep people and permissions changeable from the shared item, and don't show a sent receipt before the destination reports success. Where the OS doesn't report completion, say only what the app actually did.

## For lmthing

Build cases with `Empty`, `KitSkeleton`, `Banner`, `Progress`, `Success`, `Sheet`, and `HandoffReceipt` as distinct status roles, not identical notices with different icons. The component guide already keeps usable cached data in `filled`, uses a trusted stale flag with `deviceDataFlags`, and gates fresh-only actions with `actions.when`; preserve that instead of adding a wire state. Audit weather caches, commerce/payment retries, paperwork uploads, and requests/team handoffs for a trustworthy pending-to-receipt path. Undo across overlapping edits, durable recovery when timing matters, and explicit stale versus queued examples are gaps to feed into the journey templates and visual rubric.
