# Sheets, alerts, popovers, and progress

## Choose the least disruptive presentation

| Family | Use and anatomy | 390-wide example and failure to avoid |
| --- | --- | --- |
| Sheet | A short subsidiary task with a title, body, and a clear dismissal. For a single-step iPhone sheet, Cancel/Close leads and Done trails when needed. Back goes to the previous step, not out of the sheet. | Use medium (about half of the expanded sheet) and large detents when progressive disclosure makes sense; include a grabber for resize and support dismissal by swipe when safe. Allow large content or a keyboard to expand. If a draft would be lost, offer an explicit keep/discard decision; don't require a gesture to close. |
| Alert | A critical, preferably actionable interruption. Short title, only necessary detail, and outcome-named buttons. | Ask before unexpected irreversible loss, not every undoable deletion. Use a safe Cancel with a destructive action. Don't put routine confirmation, a loading screen, or a long form inside an alert. On native use semantic roles and let the system lay out the buttons. |
| Action sheet | A short set of choices following a deliberate action. Brief context if necessary, actions, and a safe cancel path. | After “Remove photo,” distinguish removal from this album versus irreversible deletion. Reserve it for consequential or user-initiated choices; use a More menu for ordinary commands. Avoid a scrolling action sheet. |
| Popover | An anchored temporary view with a small amount of supporting content or controls. Normally one at a time; resizing should preserve the anchor relationship. | Prefer a sheet or appropriate menu on compact iPhone rather than forcing a large anchored bubble. Outside dismissal of a nonmodal inspector must not lose edits. Don't use a popover for urgent warnings or cover it with another transient view. |
| Progress indicator | Track/bar or circle, real progress if measurable, optional context and a cancel control where meaningful. | Keep the indicator near the work and don't swap a spinner for a bar with a different footprint; a bar may shift from indefinite to measured. Report real progress, avoid impossible ETAs, and explain if stopping discards output. A spinner is not a durable failure state. |
| Gauge or goal ring | A reading or progress toward a goal, not necessarily an active operation. Show the current value, range/target and unit; give threshold meaning without color alone. | Don't use Apple's Activity rings for arbitrary data: the Move/Exercise/Stand design has specific meaning. Use neutral ring/bar geometry for generic goals and keep an accessible textual value. |

Prefer inline edits or a pushed screen for sustained or multi-step work. Avoid stacking sheets from the same parent. While a modal is active, the covered screen isn't actionable; on dismissal return keyboard and assistive focus to the opener (or a logical successor if the opener was removed). On web, use appropriate dialog semantics with a name, keyboard dismissal when safe, and an inert background for actual modals. For a nonmodal popover don't trap focus as if it were a modal. Native system sheets handle gestures and presentation changes; verify what your custom web approximation does at keyboard and reflow sizes.

## For lmthing

Core `Sheet` uses `KitSheet`; `PhoneScreen` already owns modal focus containment, restoration, dismissal, and confirmation. Keep the safety boundary there; don't implement destructive intercepts as duplicate authored sheets. Audit detents, unsaved dismiss, and meaningful action-sheet versus alert choice as host capabilities. Use `Progress` for measured work or a goal, `KitSkeleton` for unknown content structure in flight (matching the filled slots), and `Banner`/`Success` for feedback that doesn't deserve a modal. Use the guide's split between local inference and host-owned outcomes for imports, reservation flows, and export queues. Add reduced-motion and repeated-cancel evidence to the visual rubric's existing state checks.
