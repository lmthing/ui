# Motion, gestures, and haptics

## Plan behavior, not decoration

Specify what **enters, changes, acknowledges, exits, and happens under Reduce Motion**. Use movement to connect a cause to its effect, explain direction in a hierarchy, or retain identity through layout change. A control should answer a press immediately, not wait for a network reply or the end of its own animation. Let people cancel and reverse an in-flight transition. Don't spend their time animating every use of a very frequent control. Save playful motion for a task-defining moment rather than sprinkling loops through every screen.

| Moment                           | Normal behavior                                                                                                                                                                               | Less motion                                                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Enter or return                  | Push in the direction of the hierarchy, or reveal from a meaningful source. Preserve parent scroll and return focus.                                                                          | Replace spatial movement with immediate settle or a short opacity transition. Maintain title, focus, and return cues.              |
| Change or reorder                | Animate retained objects from their current positions; leave nonparticipants anchored. Update a selected label/thumb continuously under the finger.                                           | Settle position and show explicit selection or updated text. Keep direct manipulation if useful, but remove the autonomous bounce. |
| Press, detent, or completed work | Use an immediate quiet pressed treatment, then appropriate acknowledge/reject feedback. Optional haptic attaches to a meaningful boundary or committed event.                                 | Use state and text first; haptics remain a separate preference. No essential cue depends on movement.                              |
| Dismiss or cancel                | Reverse the relationship that introduced the surface. If a drag ends below the decision threshold and with little momentum, settle it back. Focus returns once; stale completions do nothing. | Direct dismissal and focus restore, or a simple fade. Don't slide the whole stage just to show the new state.                      |

## Timing and springs

Apple doesn't prescribe a universal duration/easing table in the HIG. The WWDC23 spring model distinguishes **perceptual duration** (how long it feels) from **settling duration** (when numerical error and velocity have become negligible). It doesn't require input, focus, or business state to wait for the latter. Select duration for pacing, then bounce for character. Apple's talk uses zero bounce as the general starting point, around 0.15 for a subtle brisk end and around 0.30 for noticeably playful overshoot, with caution above about 0.4. `smooth`, `snappy`, and `bouncy` are related native presets, not interchangeable with other libraries' identically named tokens. Apple's older fluid-interface talk starts at a damping ratio of 1 for an animation from rest; it gives 0.8 for a particular gesture-driven dismissal. Damping ratio and Apple's `bounce` parameter are not the same number.

As a **390-wide kit trial**, use the existing 120/220/420 ms token tiers as reference pacing for feedback, small local changes, and occasional larger transitions. These are not Apple constants or exact spring settle times. Try a quick ease-out on opacity entering and a brief fade on exit; for an isolated nongestural movement from rest, ease-in-out keeps start/end velocity smooth. Use a spring for movement under changing targets, where a static cubic curve can't pick up release velocity. Linear is reasonable for a constant-rate spinner, not for a sheet starting and stopping from rest. Keep opacity in bounds and don't let overshoot cause clipping, missed taps, or false displayed values. Comparing systems, Material 3 Expressive names spatial and effects springs separately. Borrow that distinction for discussion, not Google's tune values or a requirement to bounce on iOS.

## Direct manipulation and feedback

1. Follow the finger or pointer as soon as the gesture is recognized. Use the grabber, target, or highlighted item to expose what is being manipulated. Resolve competing gestures by intent and respect reserved system edges and standard scrolling.
2. On release choose a legal destination using position **and** velocity. A fast short flick can carry toward the next detent; a slow hesitant pull should settle back when appropriate. Don't allow momentum to skip a critical confirmation. Start the spring from the current presentation value and release velocity, and retarget from the current value and velocity if interrupted.
3. Commit the action once when intent is resolved, not at every preview frame. Restore state if cancelled and stop stale callbacks. In reorder, preserve item identity; in a virtualized list, test an item changing height while another is focused. For essential actions, offer buttons/menu commands or keyboard paths, not only a swipe, drag, multi-touch, or hover.
4. Pair visuals and haptics around the same event: selection ticks at actual value boundaries, impact at a meaningful contact/snap, and notification success/warning/error on an actual result. Don't vibrate every frame, replay a detent tick during the settle or report a successful save before the host confirms it. Prefer standard native feedback and make haptics optional; respect audio settings for sounds. On web, rely on visible and accessible state, not assumed vibration support or equivalent OS haptic patterns.

Use system transitions and preferences on native; custom gestures and motion need device verification. On web subscribe to `prefers-reduced-motion` and test changed preferences mid-flight; keep keyboard/pointer parity. For reduced motion remove decorative parallax, large travel, zoom, depth shifts and blur transitions; use static states or short fades, without disabling task feedback. Feedback remains understandable silent, eyes-free, or with motion off.

## For lmthing

The kit has `KitMotion`, `KitPresence`, motion tokens, signature hooks and host/OS reduced-motion plumbing. Catalog arrival currently uses an eight-unit rise and 40 ms stagger capped at six; reduced motion uses fades or end states, and agent mode reads the end state. Reuse these instead of per-pack styles. Audit `Sheet` detents, `SwipeStack` and pack reorder, `Segmented`/`Choice` selection, and `Progress`/`Success` live updates. The shared scalar RAF driver takes a start position but initializes velocity to zero, so prove continuity before claiming native-quality interruption; investigate shared velocity carry, haptic semantics owned by the host, and a nonspatial fallback for each signature. Keep the stage's gesture priority and the stable part address independent of interpolated geometry.

Add frame-sequence review to the visual rubric. At 390 wide inspect first response, midpoint, release, reverse or retarget, and end state, then repeat with double tap, swipe cancel, and Reduce Motion. Check first response, no visible jump, no unexplained delay in input, identical outcome/address, and no duplicate feedback; profile on a real native device and a phone-class browser before claiming they feel equal. Reserve signatures for a meaningful transformation or completion, not a new motion theme per component.
