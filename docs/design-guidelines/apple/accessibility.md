# Accessibility as interaction parity

## Reading and perceiving the interface

- **Size and reflow:** 44 × 44 pt is Apple's default iOS control size (the HIG table also lists a 28 × 28 pt minimum). Keep 44 × 44 as the proposed routine builder target and add space between controls; don't use the smaller number as permission to crowd a form. Support at least 200% text as a practical verification point and test through AX5 on iPhone. Reflow rows into columns of text at large sizes rather than clipping them. On web, WCAG 2.2 AA uses 24 × 24 CSS px or defined exceptions for targets, while 44 × 44 is the enhanced AAA target with exceptions. Use 44 CSS px as the cross-platform product default, not as a statement of WCAG AA. Also test web text at 200% and reflow at 320 CSS px, not just at 390.
- **Contrast and state:** use 4.5:1 for regular text; web AA allows 3:1 for large text (at least 18 pt regular or 14 pt bold in WCAG's web definition), and asks for 3:1 for essential control boundaries/states and graphics. Verify contrast, light/dark, Reduce Transparency or opaque fallback, and differentiated states independently. Pressed, focused, selected and disabled are different states. Use labels, changes of shape or position, and lines/patterns as alternatives to tint. Don't make chart values dependent on hover or vision; describe the primary takeaway and expose labels, units, and values. Audio Graphs on native can make patterns explorable but don't replace a clear summary.
- **Audio and motion:** provide captions or transcripts where applicable, and an equivalent visible cue for sounds/haptics. Don't play nonessential audio on a silent device. Honor Reduce Motion, remove repetitive/peripheral movement, depth jumps, and flashing, and provide a still or fade that carries the same meaning. Support stopping nonessential sustained activity. Use ordinary spoken words to describe a status rather than asking the person to infer it from the animation.

## Operating the interface

Give each action a concise name, role, state/value and when useful a hint about what happens next. Prefer one logical focus stop for a simple actionable row, but keep a distinct trailing action reachable if it does something different. An icon-only Clear button should name what it clears; a rating should expose its scale and value; a custom slider should be adjustable. Keep focus order close to source/reading order. Ensure decorative chevrons, skeletons and visual duplicates don't create empty announcements. Visible label text should appear in the accessible name so the person can say it to Voice Control.

Give a visible and keyboard-accessible alternative to drag, swipe, hold, hover, or multi-touch when those are shortcuts to an essential action. Native tests must include VoiceOver, Voice Control, Switch Control and Full Keyboard Access where applicable; don't infer success from labels found in code. Test with Assistive Access when relevant: focus on the essential task, simple choices, and consistent clear exits.

When a dialog opens, move focus into it, prevent access to the dimmed parent, and restore focus when it closes. On list row removal, choose a logical adjacent item as fallback. Don't move focus merely to report background progress. For error and status messages, announce the meaningful transition once; avoid reading every update to an animation or a countdown. On web use semantic elements, native tab order, visible focus, correctly scoped live regions, and check hardware keyboard travel and assistive technology on mobile Safari. An automated scan can spot missing names, not whether the task is understandable or doable.

## For lmthing

`PhoneScreen` provides modal containment and restoration; the guide specifies accessible `KitSlider`, `KitCheck`, and addressable actions. Test `Search` with results arriving, `Field` with a validation error and the keyboard open, `SwipeStack` with a non-swipe route, `Gallery` and charts with accessible reading, and data/health/finance packs with a nonvisual comparison. For voice, keep spoken and typed paths equal and show the same state and reply in text. A stable `screen/component/item/part` address isn't a user-facing label. Propose a filling/reflow/focus and preference matrix for the visual rubric, plus device acceptance on iOS and Safari web. Don't mark an accessible feature supported solely from a screenshot or DOM scan.
