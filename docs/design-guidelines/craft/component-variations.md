# One component, four different apps

Start with the same component job and stable anatomy, not four bespoke renderers. Change which data is primary, the arrangement and accessories that make it scannable, the finish and tone, and when it earns motion. The component's job, required information and reachable actions are unchanged. Use a dedicated pack component for a genuinely different job, state machine, domain record or required consent; don't smuggle those in as styling.

## A collection of actionable items: one `List`

Use a leading anchor, label, optional supporting information, optional trailing state/value and one predictable row target. On a 390-wide screen the kit's 20-unit gutters give a 350-unit column. Give the middle text flexible width; reserve enough for the longest meaningful trailing value before making a row compact.

Dense means less vertical padding, not a smaller touch region. Keep 44 pt iOS, 48 dp Android and the kit's 44 CSS px web baseline. If a row both navigates and has a separate toggle, give the toggle an independent target and name; don't attach a second invisible action to the same tap. Separate selected, checked, pending, disabled and warning semantics. Preserve the same order and facts when switching to keyboard navigation or assistive technology.

**For lmthing:** These are directions to prototype with actual `List` axes, not new props or promises of exact heights. Use the kit row/cell recipes, `useVariant()` and `variantParts` for visible/accessibility changes; the alternate role above should remain recognizable with a neutral preset. Switch to `Transactions`, `HabitGrid`, dispatch `StopHandoff`, or kids `VisualRoutine` if domain behavior actually exceeds a general list. Gap: assess address persistence and option visibility when a loaded list changes arrangement, density or filter.

## A featured object: one `Card`; a completion read: one `Progress`

| Domain    | `Card`: stable title, optional description/media, existing action                                                                                                                              | `Progress`: stable label, value/total (where real), and visible indicator                                                                                              |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fintech   | “Transfer to Alex”; `media: none`, `detail: full`; exact amount, currency and status before any action. A neutral surface can still have confident type.                                       | Use `figures: exact` for measured debt/goal progress. Pending transfer is a named phase, not 67% unless a defensible denominator exists.                               |
| Wellness  | “Today's recovery”; `media: icon`, `emphasis: hero` for the one useful recommendation; rest is a first-class content outcome.                                                                  | A ring can foreground a bounded session; include a label and count such as 2 of 4. No value implies care is needed or a goal is compulsory unless genuinely true.      |
| Logistics | “Stop 04 · Receiving”; `media: none`, `detail: full`; warning tone only for an exceptional condition. Keep times and actionable destination stable during refresh.                             | `figures: exact`, “7 of 12 stops”; text separates ETA from percent and marks estimate freshness. Do not draw a map route or a progress jump for a fabricated location. |
| Kids      | “Build a boat”; `media: cover`, `detail: brief` with simple illustration and one visible action. Use a landscape crop if appropriate to the asset and actual slot, not as a guessed Card prop. | Hero progress at a concrete milestone; 3 of 5 with familiar marks beats an abstract score. Static final result is just as understandable.                              |

Card does not own every state above; pair it with supporting `Banner`, `Note` or a pack-specific status when needed. A meaningful data-specific variant beats a wallpaper: if what the person sees first, how they scan it, or what response they get is identical, choosing a different accent alone is not a new design. Keep a coherent repeatable art treatment, not a different aspect/radius per item. When exact and shortened figures are both useful, exact is still available where it affects a decision.

**For lmthing:** Example combinations, not new enums: `bold` + `calm` motion for a crisp finance screen; `calm` preset + quiet cadence for recovery; `fresh` with `compact` density for utility; `playful` plus `lively` _only for eligible moments_ in a children's activity. Test the default before selecting a variant; select only combinations actually declared in the schema. `emphasis` preserves all parts, while `media`, `detail`, `lead`/`trail` and collection options may change what is drawn and must declare affected parts. Preserve old item IDs and action scopes through the changes. A `brief` state cannot be accepted if it hides the payee, freshness or consequence of a decision. For kids, `ParentGate` is a host admission contract, not a trophy or a generic button to restyle.

## Review variations as compositions

1. Start with the main task and a realistic record including a long localized label, a long value and an absent asset. Build the 390-wide screens with the same component IDs and representative states (loaded, empty, waiting, error, success where meaningful).
2. Compare the variants without their accent colors: does the lead, density, expressive focus or useful state still read differently? Compare with the current `List` exemplar. Then check both themes for contrast, 320-width and enlarged-text reflow, not just the intended 390 composition.
3. Exercise the same tap/keyboard/screen reader result in each variant. iOS and Android may differ in navigation, pen/finger behavior or native feedback; web needs visible focus, reliable keyboard operation and no hover-only actions. Run a sequence review for the specific cue and its reduced-motion result.

**For lmthing:** The next synthesis should connect the visual-rubric variants sheet to a cross-domain comparison and correlate screen recipes with the catalog's real addresses and UI read. Only propose a new axis when several unrelated components share the same semantic choice and the effect cannot already be expressed by an archetype, theme, signature, pack or existing axis. No axes are added here.
