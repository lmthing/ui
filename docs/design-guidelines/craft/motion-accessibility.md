# Motion: sensory feedback, reduced motion, and review

## Use one event, with optional sensory layers

| Meaning                    | Visible baseline                                                  | Optional on supported native devices                                                  |
| -------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Selection snap or detent   | A mark, stable label, or thumb lands on a named value.            | One selection tick on crossing a real increment, never a buzz per drag frame.         |
| Physical contact           | An object visibly seats or a control clicks into place.           | A light impact timed to contact. Don't double up native control feedback.             |
| Authority-confirmed result | A static state label or receipt states the outcome and next step. | A success tone or notification haptic at the visual beat. Don't reuse it for failure. |
| Urgent, actionable failure | The problem and fix remain readable near the action.              | A short, distinct warning if helpful; never repeat it on a timer.                     |

On iOS use documented selection, impact, and notification meanings and respect silent mode for nonessential sounds. On Android prefer the platform action's haptic constant over raw vibrator waveforms, respect system feedback settings and omit unsupported effects rather than substituting a long buzz. On the web assume neither haptics nor autoplay audio works; no result should depend on either, and optional sound must honor browser playback rules and switch-off. Put sound and haptics on the same event as the visible state, not on independent timers. If there is a voice or mic session, incidental effects should not compete with speech or interfere with recording.

Pok Pok is a good calibration for frequency: its designers recorded tactile sounds for distinct objects, then tuned and reused them so repeat play wouldn't exhaust a child or nearby adult. That design choice is more transferable than a mascot or a chime. Try hearing a signal twenty times while using the feature before keeping it. Offer independent controls for nonessential audio and haptics where relevant; motion opt-out is not consent to a compensating buzz.

**For lmthing:** `Choice`, `Calendar`, `Scale`, `SwipeStack`, `Checklist`, `Success`, kids `SoundGrid`, and mind `Breathe` are starting points. Keep semantic event → optional host feedback separate from `useSignatureProgress`; playback remains a deliberate action for soundscape/audio features. Propose a host capability and preferences contract instead of direct vibration from React views or instructions for a model to author waveforms. Exercise mute, missing actuator, TalkBack/VoiceOver, microphone use and repeated actions.

## Ship equivalence, not shorter vestibular motion

Reduced motion is an alternate treatment with the same facts, control labels, focus, and reachable outcomes. Prefer immediate final layout or a short opacity-only handoff (about 100–120 ms, not a mandate). Remove automatic pan/zoom, parallax, spring overshoot, big transforms, moving masks, looping shimmer and confetti. A finger-controlled slider or precise drag can still follow the finger where movement is the input; remove decorative release motion and provide an equivalent non-drag control. In a paced experience such as guided breathing, offer a static phase label, remaining time and pause; optional sensory cues never become required.

- **Native:** Honor iOS Reduce Motion and the Android platform animation preference via the host. Observe changes while mounted. If the preference flips during a spring, cancel and resolve to the correct state with no loss of focus or pending data. Leave native navigation's accessibility treatment to the platform.
- **Web:** Respect `prefers-reduced-motion: reduce` in CSS and the runtime driver, including changes after mount. Preserve visible focus; don't use a late animation callback to unhide meaningful content. WCAG 2.2's Animation from Interactions (2.3.3) is AAA, not an AA minimum. Separately check the AA status-message criterion (4.1.3) and the A pause/stop/hide conditions for automatically moving content (2.2.2). Prevent flashing; reduced-motion mode alone is not a substitute for a safe default.
- **All:** For visual contrast at rest and at actionable intermediate states, use at least 4.5:1 for normal text and 3:1 for large text and essential control graphics under the corresponding WCAG criteria. Use a 44 pt iOS and 48 dp Android target baseline (44 CSS px kit baseline on web); check actual hit regions with a keyboard focus indicator and safe area. Do not dim the sole visible status into illegibility as it changes.

**For lmthing:** The plan calls for `calm` as a neutral theme, `lively` for eligible flourishes, and OS preference to win. `PhoneScreen` subscribes to the OS through its environment; the extra `KitProvider` OS hook is conditional on `lively`. Currently `KitMotion` checks the environment rather than the theme and can still collapse height on exit in reduced motion. `useSignatureProgress` checks the supplied cue, agent mode, and reduction, but does not itself check theme motion. Audit these paths before treating `calm` as no spatial motion or reduced motion as opacity-only. Agent mode should keep the same end values and addresses. Apply the same motion preference to the stage and the phone content, not only the selected component.

## Review a sequence, not a still

At 390 logical width, capture rest → first visible response → midpoint near maximum overlap → settled state, plus a slow reverse and a fast interrupt. Compare reduced, default and expressive from the same input and final state. For typical device refresh, 60 Hz leaves about 16.7 ms per frame (120 Hz about 8.3 ms); measure on an ordinary phone, and prefer one cheap visual layer instead of many changing layouts or heavy live blur. Check direct touch and keyboard, screen reader announcement once, actionability during motion, low-power/weak device, background/reopen and a preference switch mid-flight. A 100 ms fade that holds input for 100 ms still fails the interruptibility test.

**For lmthing:** The visual rubric and `look` stills remain useful for hierarchy and clipping. Add sequence fixtures for `Sheet` cancellation, collection removal/undo, overlapping state updates, and a host-accepted receipt with the cue interrupted. Existing `test/motion.browser.test.ts` covers the ring cue and reduced-motion/agent end states, not all app transitions or native frame pacing. Test on-device with actual native adapters before declaring parity.
