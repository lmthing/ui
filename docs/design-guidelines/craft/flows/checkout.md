# Checkout: payment and fulfillment are separate

- **Cart → details:** Keep item, quantity, variant, availability and the price breakdown attached to the cart. Only ask for necessary contact and fulfillment information; preserve edits, expose guest checkout when applicable and allow supported autofill. Mark taxes/shipping that are estimates. If a coupon, address or inventory change alters the total, explain it and require a fresh review.
- **Review → authorization:** Put merchant/payee, items, delivery or pickup, subtotal, fees, discounts and exact total/currency above the final action. A button such as “Pay $42.50” gives a precise consequence. Use real platform wallet controls where supported, never style an ordinary button to imitate them. Make Back or cancellation from the wallet restore the checkout draft.
- **Processing → settled:** Disable duplicate submission for the same attempt, not the whole screen; allow safe departure and status lookup. Separate bank authentication, canceled authorization, pending payment, failed payment, paid, and fulfilled. On a timeout after sending, reconcile the attempt before asking the person to pay again; preserve non-sensitive inputs. Show payment-confirmed receipt reference and separate order status; give recovery for failed payment/refund rather than retrying a completed order. Never include card data in a preview receipt.

Apple Pay's design guidance ties wallet presentation to capability and provides integral checkout; Google Pay also prescribes role-appropriate branded payment controls. Stripe documents that a browser reaching the success page isn't an authoritative settlement signal, and that delayed methods can settle later. On native return from the system sheet to the same record. On web, allow a hosted/redirect return and reload into the authoritative state rather than treating a success-looking URL as proof.

**For lmthing:** `pay_receipt`, `commerce`'s `Cart`, `Checkout`, `OrderSummary` and `OrderStatus`, and `customers`' `Invoice` and `PaymentStatus` cover the main surfaces. `Amount`/`KeyValue` show exact money, `Steps` shows meaningful stages, and `Success` is not a provisional reply. Use host command pending/terminal states and safe duplicate handling in the adapter, never animation or a model-supplied link as the authority. Gap: distinguish payment accepted, settlement unknown and fulfillment in the preview fixtures; label demo-only submission clearly.
