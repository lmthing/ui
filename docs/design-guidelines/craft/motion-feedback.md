# Motion: actions, numbers, progress, and celebration

## Make the response match the event

| Event                              | What to show at 390 wide                                                                                                                                                              | What it must not say                                                                                                |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Finger down or keyboard activation | Use a pressed tint or about 3% visual compression on the button face; keep its hit bounds fixed. Give keyboard focus its own visible treatment.                                       | A press is not a completed action.                                                                                  |
| Toggle, pick, or snap              | Move the thumb or selection mark into place; also change text, checkmark, or accessibility state. Try one fast token (120 ms) for a small visual effect.                              | An ordinary selection doesn't warrant a burst.                                                                      |
| Reorder or remove                  | Let neighboring rows close the gap as the origin leaves; put undo where it can be found and keep the record identity stable.                                                          | A fading outgoing row isn't still actionable.                                                                       |
| Submit                             | Keep the label's width and button position; show pending beside or inside the initiating control, with scope and a safe way out.                                                      | Never play success on tap, on timeout, or on opening another service.                                               |
| Error or warning                   | Put a persistent, readable message near the problem with a recovery action; use a modal only for a necessary decision. No shake required.                                             | Do not signal by color, bounce, vibrate, or toast alone.                                                            |
| Confirmed milestone                | Reveal one focal object then the outcome text and continuation. A localized one-shot reveal around 220–420 ms is a starting point; the receipt and next action are ready immediately. | No blocking replay on reopen, no automatically launched share, and no confetti over dangerous or ambiguous actions. |

Duolingo's own milestone account shows the difference between everyday checking-in and a notable achievement: its character changes form at milestone values, while the number and shareable end state carry the meaning. Its team also found that a flame metaphor didn't explain streaks to everyone. CapWords, Apple's 2025 Delight and Fun winner, uses an object-to-sticker transformation and real-world sound in flash-card transitions. Borrow that causal link between input and outcome, not the assets. A money transfer wants a legible receipt, not a victory sequence; a well-earned learning achievement can afford a stronger beat.

**For lmthing:** Reuse `KitAction`, `KitCheck`, `KitPresence`, `Success` and existing signatures such as `check_burst` and `streak_flame`. Choose one deliberate cue per meaningful event; if the same event is rendered after reconnect, route restore or an agent read, show the static end state. `useHostOperations()` makes accepted/rejected/cancelled distinguishable from merely staged. Keep confirmed effects on the host's authoritative outcome and distinguish confirmation of a request from confirmation of the thing requested. Add interaction fixtures for repeated events, fast cancel and late success.

## Make waiting truthful and geometrically stable

Material's progress guidance gives useful conditions, not backend deadlines: under 200 ms usually needs no separate indicator; 200 ms to 5 s calls for a loading signal; beyond 5 s use fuller progress feedback. Prefer measured progress whenever available, regardless of the band. Apple prefers determinate progress and recommends preserving the indicator geometry when changing from unknown to known progress. Don't invent a percentage or fill to 90% and hang. A practical sequence:

- **Initial load:** A header, stable navigation and any available content render first. If structure is known, skeletons take the actual row rhythm: e.g. icon/thumbnail slot, title, one secondary line and an end accessory at the real gutters. Use a static skeleton by default for uncertain waits; animated shimmer is optional, never semantic, and stops offscreen or in reduced motion. Skeletons aren't controls, content or extra screen-reader stops.
- **Refresh:** Leave usable data in place. Use a small local activity indication plus freshness when relevant. A short button or row request doesn't replace an entire screen with ghosts.
- **Slow or stalled:** Say what is happening and offer cancel, retry, or leave-and-check-back when those actions are real. For a resumable transfer, show actual units or current stage. If connectivity fails, distinguish last known data from no data and from no results.
- **Handoff:** Keep gutter, focus, and scroll anchor; reserve media aspect ratio and the space for a one- or two-line title. Replace only the settled placeholder slots. Choose infrastructure for a polite busy/status announcement, then announce useful state boundaries, not animation frames.

**For lmthing:** `KitSkeleton`, `KitCard`, `List`, `Gallery`, `Progress`, `Checkout` and `FlightStatus` cover the main cases. The visual rubric already asks loading to match filled shape. Add refresh-with-data and stale-with-timestamp examples in addition to first-load snapshots. Pack state policies should describe what stays actionable and whether an in-flight local cancel can affect a service. On web use semantic progress and a separate status message, on native use accessible values/announcements and host refresh behavior.

## Animate a value without making it untrue

Give the number fixed alignment, tabular figures where available, and enough space for its sign, currency, and unit. At 390 wide, a summary number can use the kit's 40/44 number role, while row values share a right edge and avoid width changes for 999 → 1,000. Animate decoration or a delta first for fast-changing sources. Choose the transition from the data's meaning:

- A decorative onboarding KPI can count once over the slow token. Keep the real value available to assistive technology from the start. Retarget from the displayed value when the illustrative target changes.
- For an authoritative total, balance, medication dose, negative amount or time-critical ETA, update actual text immediately. A restrained highlight on the changed cell, not fabricated intermediate numbers, explains the change.
- A real determinate ring or bar can interpolate the fill independently of the text. If the maximum changes or the process restarts, label the change rather than pretending progress always rises. For frequent live numbers or timers, update at meaningful precision without bouncing or announcing each tick. Respect locale, decimal precision, reading order and sign.

**For lmthing:** `Stats` has `count_up`; `Progress`, `Bars`, `Amount`, `Counter`, `Timer`, `AccountCard` and `FlightStatus` need rules for which values may interpolate. The existing `countText` helper derives an intermediate display from a formatted string rather than raw typed data. For future generalized use, propose a shared renderer fed raw typed values and the same locale formatter as the final state, with the real value exposed once to the reader. Test zero, sign change, currency and separators, rapid replacement, thresholds and reduced motion.
