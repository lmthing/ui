# Patterns and flows

A template is a sequence of roles, steps, branches, record bindings and inspectable states. An archetype is a screen layout, not a journey. A gallery playback is a mock, not a transaction. Use a template only if its intent and outcome match; keep the `waiting` flow frame distinct from a component skeleton and from a host accepting a request.

## Built templates

| Job and template                                              | Review these facts along the way                                                                                                                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Booking · `book_slot`                                         | Local time and service in selection and review; reference in confirmation. Reschedule keeps the old booking until settled; cancellation has a review. If the slot is lost, offer another without clearing context. |
| Waitlist · `class_waitlist` (booking)                         | A queue place and an offered seat are not a booked seat. Check acceptance or expiry with the same class/date and person.                                                                                           |
| Checkout and receipt · `pay_receipt`                          | Show amount, order, payee and final receipt. Processing, failure and paid look different. Never double-charge on retry or imply a real payment in a sample.                                                        |
| Order tracking · `order_track`                                | Follow review → preparing → transit → delivered. Keep order ID, latest dated update and expected next milestone; no fake live location.                                                                            |
| Approvals · `request_approve`                                 | Show requester draft, submitted/waiting and accepted or rejected with reason. The approver reviews the same record and can choose a real branch.                                                                   |
| Access and invitations · `invite_accept`                      | Preserve invitee and scope. “Invited,” “Waiting,” and “Joined” are distinct. Include wrong/expired invite and a safe return.                                                                                       |
| Onboarding · `signup_onboard`                                 | State what setup is for, verify, let optional preferences be skipped where safe, then land on the first meaningful task. Auth is demonstrative and host/service owned.                                             |
| Issue and resolution · `report_issue`                         | Keep issue reference, evidence, resolver and resolution tied together. “Reported” isn't “Resolved.”                                                                                                                |
| Dispatch and acknowledgement · `assign_work_order` (requests) | A dispatch, an acknowledged assignment and completed work are separate outcomes. Keep work-order reference, assignee and next job in both roles.                                                                   |
| Check-in · `check_in`                                         | Attendee pass and host record refer to the same reservation. Cover not-found and already-recorded; never label a displayed pass as arrival.                                                                        |
| Client intake · `lead_to_client` (customers)                  | Preserve lead context through follow-up and conversion. Distinguish a prospect's submission from a staff-side conversion.                                                                                          |

## Composition patterns without an end-to-end template

| Pattern                    | Compose now                                                                                                      | Missing template proposal and acceptance                                                                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Search/filter              | `browse` or `list` + Search, FilterBar/Choice, List, Empty                                                       | `find_and_filter`: zero matches retains query/chips; clearing restores results; opening/back restores prior scroll and scope.                                                            |
| Messaging                  | `chat` + Bubbles and Composer; use `invite_accept` only for actual invitations                                   | `message_reply`: draft → send acknowledgment → other role's incoming message/reply. Include failure/retry, send vs delivery versus read, and unavailable thread.                         |
| Settings                   | `settings` + SectionTitle, List, Choice or supported Field                                                       | `change_preference`: view current → edit → save or undo → reopen with actual choice. Include unsaved Back and a failed remote save.                                                      |
| Profile                    | `profile` + Profile; use `form` for changes, `capture` for photo as needed                                       | `edit_profile`: preserve identity across view, editable fields and receipt; retake/remove photo, distinguish private/public visibility and denial.                                       |
| Checkout before payment    | Commerce Cart/Checkout → `pay_receipt` as applicable                                                             | `cart_to_order`: edit quantity, unavailable item/price, pickup/delivery and review before payment; preserve item counts and totals into order tracking.                                  |
| Transfer of custody/status | HandoffReceipt on both sides; reuse `report_issue`, `check_in` or `assign_work_order` only for their actual jobs | `transfer_acknowledge`: handoff can be sent, received, declined or late; receiver uses the same reference and can act from its queue. Useful for donation, logistics and shift handover. |

## What to verify on every flow

1. Give the first screen a credible working object, a visible job and one next action. Put the date, amount or decision before prose. Label Inspect separately from Play; an example of a control is not a live transaction.
2. Carry the same sample reference and key facts through review, commit and receipt. On handoff, evaluate each role separately on the same record. Only an acknowledged result advances to confirmed. Approval sits with the approver, not the requested action; no success on a missing receiving path.
3. Exercise empty, waiting, rejected, retry, Back/no commit and success where meaningful. Keep the draft on recoverable errors; after wait/relaunch show latest known state, not a new duplicate. For irreversible actions provide a specific review; for safe reversible changes offer Undo.
4. Read the return path at 390 light: don't lose the selected role, scroll, query or focus. Keep navigation and the stage player from covering the task CTA. Show the minimum changed region from first to final frame. Copy names the object acted on, not an internal step id.
5. Re-check UI, host and orchestration separately. A clipping or parity bug is a kit finding; an absent journey, wrong generated status or unimplemented transport belongs to the harness/app that owns it.
