# Selection and input

Separate four intentions: filter a collection, choose a value, change a setting immediately, and edit a draft that is submitted later. Show independent pressed/focused and persistent selected/checked signals. Never make a result depend on a specific drag, hover or unlabeled color change.

## Chips and discrete controls

| Component           | Anatomy and states                                                                                                          | Use at 390                                                                                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Assist chip**     | Rounded container, short label, often leading icon; can be elevated for separation.                                         | A contextual shortcut from nearby content, not a replacement for the screen's main button.                                                                                                                                                                      |
| **Filter chip**     | Label, selected/unselected states, optional leading icon/check and applicable trailing disclosure. May be flat or elevated. | Apply a visible filter to the nearby result set. Offer clear/reset for multiple filters and maintain result position where it remains meaningful.                                                                                                               |
| **Input chip**      | Label, optional leading avatar/icon and trailing remove action; selected/focused/disabled as applicable.                    | Represents an entered recipient/tag, not a suggestion. If the chip body edits or is draggable, keep its target distinct from Remove. M3 illustrates an 88 dp visual chip or a 42 dp label; verify that both actual 48 × 48 dp regions fit without interference. |
| **Suggestion chip** | Short generated suggestion, optional leading icon, normal control states.                                                   | Offer a next query or common entry; visually distinguish from current filters and allow ignoring it.                                                                                                                                                            |
| **Checkbox**        | 18 dp baseline box and check or mixed dash, with label and 48 dp target.                                                    | Independent choices. Mixed means a parent represents both on and off children, not a third arbitrary option. Make label and box one target.                                                                                                                     |
| **Radio button**    | 20 dp outline with an inner dot for selection, plus label and 48 dp target.                                                 | One choice in a named group. Use unlike checkboxes when picking one replaces the prior value. Provide “None” when no selection is a meaningful option, or a clear/unset action.                                                                                 |
| **Switch**          | Track and thumb, optional icon, and label; baseline Compose track 52 × 32 dp.                                               | A setting that takes effect now; position as well as color change, with stable label across states. Use a checkbox or radio in a deferred form, not a switch that silently waits for Save.                                                                      |

Chips commonly have an 8 dp corner and 32 dp body; reserve 48 dp in the layout where interactive. Wrap or use an accessible overflow strategy, rather than packing targets together. Show checked/selected/mixed in semantics on top of normal interaction states. Web use native checkbox/radio controls when possible (native radio groups provide keyboard selection) or a correct custom role; native toggleable/selectable controls can apply the behavior to the full row. Do not let both row and child emit the same action.

### For lmthing

`Chips` and data `FilterBar` support filters, `Choice` supports substantive choices, `Checklist` tracks completion and `Field` can own form choices or settings. Apply the right single/multi/toggle semantics to each declared part. Gap: a consistent mixed-state and distinguishable remove target policy where those needs actually recur.

## Sliders and scroll fields

- **Slider:** Track, filled portion, thumb, optional discrete stops, labels/value bubble; continuous, discrete or two-thumb range. Set useful endpoints, unit and increments. Expressive lists five visual sizes, 16/24/40/56/96 dp (XS to XL), with XL reserved for the focal control. Keep active and inactive tracks the same thickness and avoid inset icons below 40 dp track thickness. These dimensions aren't a substitute for the actual hit area. Keep the thumb accessible and show current value without requiring focus or dragging. In a range, name both ends and prevent crossing targets unless the product explicitly supports exchanging their meaning. Use steps or a number field when exact entry matters.
- **Scroll field:** A wheel-like numeric control with focused center value and neighboring values, plus a keyboard input mode. Inline placement is preferred; modal/nonmodal are alternatives. Current guidance suggests widths of 100 dp for 1–2 digits, 144 for three and 186 for four. Do not wrap at numeric bounds unless the domain is naturally cyclic. Provide min/max, step and a typed path, and avoid stealing vertical page scroll.
- **Behavior:** On native a drag should track the finger and settle to a valid value without overrun. In web sliders offer keyboard adjustment and expose min/max/current value and unit; an `<input type="range">` can handle common single-thumb cases. Dragging needs a simple pointer alternative (tapping track, step controls or editing the number); keyboard support alone isn't enough to meet that need.

### For lmthing

`Scale`, `Counter`, `Field`, and the slider and number input kit bases should use declared bounds, step and projected value. Booking, health and money packs need precise typed or step-based alternatives more than larger decorative knobs. Gap: verify overlaps of two targets, pointer cancellation and failure reconciliation for host-backed changes.

## Text fields and search

- **Text field:** Filled or outlined container, persistent label (can float), input/caret, optional leading and trailing adornment, prefix/suffix and supporting text/count. A baseline Compose single-line start is 56 dp high; reflow for larger type or multiline rather than clipping. Filled uses a visible active indicator; outlined uses border emphasis. Match one family for a related form unless fields have deliberately different emphasis. Placeholder is an example, not the label. Keep input, focus, leading/trailing names and current error accessible.
- **Validation:** Include default, focused, filled, error, disabled and read-only cases where applicable. Replace supportive copy with a nearby precise repair message; reserve a line when errors are likely, but let real messages wrap. Do not use an error-color outline alone or erase an in-progress draft on failed submit. Set the right keyboard/input purpose, autofill and paste behavior; use a show/hide action with a stateful name for a hidden value.
- **Search:** Keep local collection search visibly scoped. Use a persistent search app bar for global search when central to the product; a search affordance may open focused search with a field, clear/back, suggestions/history and results. At compact it can occupy its own full-screen surface. Google's spacing example shows 24 dp horizontal margins unfocused and 12 dp focused, with internal gaps unchanged. Restore the query and scroll on return if the task calls for it. Show different pending, no results, empty query and offline/server error states. Debounce or cancel superseded queries, never replace a new result with an older response.
- **Platform:** On web label input in markup and use a search landmark when appropriate, accessible suggestion navigation, and a polite result-count/status update without reading every keystroke. On Android use search-specific keyboard action, consume keyboard/back in the right order, and keep results away from keyboard insets. Offer an explicit clear control so no gesture is required.

### For lmthing

Use `Field` for short form values, `Composer` for longer text, `Search` for query/result intent, and `Empty` for no results or failure. `List` and `FilterBar` should retain stable rows through filtering if still present. Gap: jointly test search focus and history, IME/keyboard, empty-after-filter, stale responses, and inline error wrapping in the supplied `PhoneScreen`.

## Date and time pickers

- **Date picker:** Month/year controls, weekday header, days with today/selected/unavailable states, optional range with start/end and intervening days, confirmation/dismissal where modal. M3 includes modal calendar and text input, docked for wider contexts, and full-screen for compact date ranges. Keep dates selectable with an accessible description even where calendar cells are spatially constrained; a 7-column calendar needs 336 dp for seven 48 dp cells before gutters. At 390, with 16 dp outer margins, that leaves only 22 dp extra on 358 dp of usable width. Avoid card-within-dialog padding that breaks targets; consider full-screen layout plus a typed fallback.
- **Time picker:** Modal dial, scroll time picker or numeric input with hour/minute, AM/PM only where appropriate, and explicit confirm/cancel if deferred. Provide a visible input-mode toggle, not an obscure gesture. Validate on input/commit, respect locale and 12/24-hour preference and display dates/times unambiguously when a timezone matters. Announce which part of the value is being edited and keep dismissal from saving a draft.
- **Platform:** Native Android components can integrate locale, IME and accessibility; verify all three rather than assuming custom art does. Native HTML date/time input can be a good web option if the browser behavior and form semantics fit, but visuals and keyboard behavior differ; custom picker needs named controls, grid keyboard navigation and error/status semantics. Do not rewrite a calendar date into another day by treating it as a UTC timestamp.

### For lmthing

Map calendar browsing to `Calendar`, scheduled date/time entry to `Field` and the shared input bases, and compact options to `Sheet` only when they really are a list; `Timer` is elapsed/countdown, not a time-of-day picker. Gaps in booking, events, trips and health: date-range constraints with visible unavailable reasons, typed/native fallbacks, time-zone examples and real-device calendar target verification.
