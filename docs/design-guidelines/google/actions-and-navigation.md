# Actions and navigation

On a 390-wide phone, distinguish **where I am** (app bar, navigation, tabs) from **what I can do** (buttons, FAB, toolbar). Keep selection persistent and press feedback transient. Every target is at least 48 × 48 dp even when the visual container is smaller. Use named visual and semantic states, not color alone.

## Top app bars and toolbars

- **App bar:** The anatomy is container, current title, optional supporting line or image, leading back/navigation control, and usually 1–2 essential trailing actions. A small bar is the routine default (64 dp Compose small bar before system insets). Expressive favors **medium flexible** and **large flexible** over the older titled medium/large variants: use extra space for an actual headline, subtitle or image, not blank chrome. Search app bar adds persistent global search. Scrolling can take a bar to a compact state and change its surface tone. Preserve the title and essential actions; use one back control for a child screen, not an unrelated menu.
- **Toolbar:** Contains actions for the current screen or selection, rarely top-level destinations. Expressive recommends **docked** or **floating**, rather than the older bottom app bar. Use docked for consistent access; use floating for a small context-specific set, optionally beside a distinct FAB. For a horizontal floating toolbar, start with 16 dp from the window sides, 16 dp leading/trailing internal padding when using the guideline's free arrangement, and 48 dp targets. Protect content, safe area, keyboard and bottom navigation from overlap; don't add a toolbar if only one ordinary button is needed.
- **Behavior/platform:** Distinguish scrolled, expanded/collapsed, and contextual states. Use state feedback on controls without animating the full bar on each press. Android owns system status, back and gesture regions; a web header must not hide focused content during scroll, and a true keyboard toolbar should implement appropriate focus behavior. Use headings and buttons, not clickable decorative icons.

### For lmthing

`Header` and code-owned bottom chrome already separate structure from content; `Actions`, `Button` and `Sheet[menu]` can handle a short contextual action set and overflow. Gap: a kit-level grammar for collapsed headers and keyboard-safe docked/floating toolbars, not a new Writer component for each chrome variation.

## Buttons, icon buttons and FABs

| Component         | Anatomy, variants, and compact use                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Button**        | One brief verb phrase, container, optionally one icon. Filled is for the main action; tonal for supporting emphasis; outlined for a substantial secondary or escape action; text for a quiet supplementary action; elevated only when separation is needed. A common small visual button is 40 dp with a 48 dp target; Expressive includes larger sizes. The button's text color and icon role normally match. |
| **Toggle button** | Same family of containers, plus persistent selected/unselected visual and semantic state. Keep its footprint stable, use a selected mark/shape and text when meaning isn't obvious, and keep toggle behavior separate from an ordinary command that runs once.                                                                                                                                                 |
| **Icon button**   | Glyph plus target, optional contained shape: standard, filled, tonal or outlined; can also toggle. Expressive visual heights are 32/40/56/96/136 dp (small, 40, is the default). Keep the accessible name even with a tooltip; prefer a label for consequential or unfamiliar actions. Use status semantics such as pressed for a toggle and reserve disabled for truly unavailable commands.                  |
| **FAB**           | One prominent action, usually creation, with high-strength fill, glyph and elevation. Regular 56 dp is a compact default; large is 96 dp, and the old 40 dp small FAB is not recommended in Expressive. Site it about 16 dp from usable edges as a compact starting point; lift for bars and insets. Do not duplicate a filled primary or use it as a floating tab.                                            |
| **Extended FAB**  | Container with short label and optional icon; Expressive heights 56/80/96 dp. Useful when action meaning needs words or space allows it. At 390 use the small height and test long labels; collapse to an icon only if its purpose stays obvious and accessible.                                                                                                                                               |
| **FAB menu**      | A FAB opens 2–6 closely related actions under one shared intent. Keep original control as the toggle or close affordance, group and order items, and keep all reachable above lower chrome. Don't use for a pile of unrelated settings or destinations.                                                                                                                                                        |

Show enabled, disabled, pressed, keyboard focus, and on pointer platforms hover. Material's generic state-layer references tint with the content color at 8% for hover, 10% for focused or pressed, and 16% for dragged; use the component's defined recipe where it differs. These are interaction overlays, not colors for persistent selection, and do not replace a clearly visible keyboard focus indicator. Press responds immediately; availability, confirmation, or outcome comes from the action state, not an animation. Size and color should reinforce one hierarchy. In reduced motion a shape-changing press can show a static pressed state. On web choose a button for an action, a link for a destination, and use native keyboard behaviors; Android gives ripple/semantics through its components and still needs hit-region checks.

### For lmthing

`Button`, `Actions`, `Header` icon actions and `Composer` send should agree on the emphasis ladder and semantic state; a FAB can start as a host/kit recipe rather than duplicating `Button`. Confirmation stays on `confirm`/kit ownership. Gap: per-action visual size versus actual target, accessible toggle names, overlay avoidance, and explicit feedback while a host-owned action is pending.

## Groups, segmented buttons and split buttons

- **Standard button group:** Related but independently invoked actions (for example transport controls), with readable spacing and one clear lead if priorities differ. Press can redistribute visual space in Expressive; never move another control's target out from under a finger.
- **Connected button group:** Related choices share a segmented silhouette. Keep outer and inner corners coherent; show which choice is selected and whether one or several are allowed. Google recommends it in place of baseline **segmented buttons** in Expressive. Baseline segmented uses 2–5 short segments and a 40 dp visual container; use radio-like exclusivity for one option, checkbox-like semantics for multiple. If labels don't fit at 390 or large type, stack choices or use a clear alternative rather than hiding labels.
- **Split button:** Primary action and a separate trailing disclosure button for _variants of that action_, not two unrelated actions. Give both a name and independent hit areas; use open/closed state on the trailing target. Material places the menu 4 dp from its opener. Focus moves to the chosen menu option or returns to the disclosure on dismissal. For pointer and keyboard, don't treat the entire group as one link.

### For lmthing

Keep `Segmented` for existing in-page choices or view switching; `Choice`, `Chips` and `Actions` remain alternatives with different intent, not alternate paint for the same thing. Gap: connected-corner states behind kit, and a genuine two-target split-button contract only where a recurring task needs a default and alternate variants.

## Navigation bar, rail, drawer and tabs

| Component             | Use                                                                                                    | Anatomy and behavior                                                                                                                                                                                                                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Navigation bar**    | Compact and some medium windows, 3–5 equal top-level destinations; same destinations across screens.   | Icon, short visible label, active pill, optional badge; active icon/label use contrasting roles. Expressive flexible bar (Compose compact token 64 dp vs tall baseline 80) can use labels below icons at 390 and beside icons on medium widths. Don't navigate top-level destinations by horizontal swipe. Choose restore vs reset intentionally for repeat visits.   |
| **Navigation rail**   | Medium/expanded on the leading edge, or an expanded modal rail at compact when needed.                 | Collapsed rail typically 3–7 destinations and optional FAB/menu; expanded can show labels and extended FAB. Put frequent links first; adapt the shell without changing destination identity. Keep keyboard focus and selected state distinct.                                                                                                                         |
| **Navigation drawer** | Baseline standard drawer on larger windows; baseline modal at compact if destinations don't fit a bar. | Navigation list, optional headings/dividers, one selected destination; modal adds a scrim, dismissal and focus management. Expressive says to prefer the expanded rail for new designs, not remove existing accessible navigation blindly.                                                                                                                            |
| **Tabs**              | Related sibling panels _within_ one area, never an app-wide substitute for the navigation bar.         | Labels, optional icon/badge, active indicator; primary tabs for major subdivisions, secondary tabs inside them. Use fixed tabs if they fit; for scrollable tabs M3 shows 52 dp leading offset to indicate overflow. Preserve selection as content scrolls and allow keyboard movement. Swipe among peers only if the ordered relationship and gesture are meaningful. |

For web use a navigation landmark and current-page state for destinations, tablist/tab/tabpanel behavior only for real tabs. Arrow keys belong to the tab widget, and selecting a tab should not be confused with merely focusing it. Native bar/rail changes should preserve route and host back behavior. Avoid layering a bottom toolbar over the same navigation hit regions.

### For lmthing

`TabBar` is code-owned global navigation; `Segmented` is the current compact in-page alternative, not a second global bar. `Header` and `PhoneScreen` handle the local hierarchy. Gap: adaptive navigation ownership, state restoration per destination and web tab keyboard/focus behavior before adding decorative bar variants.
